# План развития FastScan Warehouse Platform

Этот документ фиксирует согласованное направление разработки. Порядок этапов
можно уточнять после пилотного тестирования, не меняя базовую архитектуру.

## Архитектурные решения

- Монорепозиторий содержит `api`, `web` и `mobile` до успешного переключения Android на собственный API.
- Backend: Node.js + NestJS, PostgreSQL, JWT access/refresh, OpenAPI/Swagger и Docker Compose.
- Основные роли: `ADMIN`, `WORKER`, `CLIENT`. Рабочие операции менеджера выполняет `WORKER`; критические настройки остаются у `ADMIN`.
- Лицензия нужна только Android-приложению и продолжает использовать существующий сервер лицензий.
- Новый API сохраняет совместимость с используемыми Android JSON-полями и складскими маршрутами.

## Этапы

### 1. Пилот мобильного приложения

- Пройти реальные сценарии: регистрация заказа, поиск клиента и трека, коробки, партии, отправка партии, неупакованные заказы и печать этикеток.
- Проверить переключение адреса API, авторизацию сотрудника, индикацию состояния API и обработку недоступного сервера.
- Исправить найденные расхождения без отключения старого API для рабочей сборки.

### 2. Полнота клиентского кабинета

- Регистрация и профиль клиента, неизменяемый клиентский код, контакты и адрес.
- Самостоятельная регистрация заказов: состав, описание, стоимость, валюта и сохранение оригинальной упаковки.
- Постоянные инструкции по обувным коробкам и упаковке сумок.
- История заказов, аналитика и внутренние уведомления; затем email/push через отдельные адаптеры.

### 3. Рабочий веб-кабинет склада

- Редактирование клиентов и заказов сотрудником.
- Полная работа с коробками, партиями и манифестами.
- Экспорт и печать манифеста со всеми согласованными полями.
- Справочники, журнал операций и административные ограничения.

### 4. Подготовка к эксплуатации

- Автоматические unit, contract и E2E-тесты критических складских сценариев.
- Резервное копирование и восстановление PostgreSQL.
- Логи, метрики, health/readiness, аудит безопасности и управление секретами.
- Тестовое окружение, миграционный прогон и план отката.

### 5. Переключение и разделение проектов

- Переключить тестовую Android-сборку на собственный API и провести пилот.
- После подтверждения переключить рабочую сборку и отказаться от стороннего API.
- Стабилизировать контракты, затем разделить `api`, `web` и `mobile` на отдельные репозитории при необходимости.

## Текущий ближайший приоритет

Пилот Android с собственным API и устранение функциональных расхождений,
параллельно с завершением обязательных функций клиентского и рабочего веб-кабинетов.
